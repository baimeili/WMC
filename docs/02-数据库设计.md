# 数据库设计

本文档描述 WMC 的 PostgreSQL 18 Schema。所有 DDL 以 `backend/db/migrations/*.sql` 为准；本文档与迁移文件不一致时，以迁移文件为准，并应同步修正本文档。

## 1. 约定

| 项 | 约定 |
|---|---|
| 数据库 | PostgreSQL 18（生产/测试）；无 Docker 开发环境使用 embedded-postgres 17 便携版 |
| 迁移工具 | goose（`-- +goose Up` / `-- +goose Down` 格式），文件按 5 位序号递增 |
| 迁移执行 | 后端启动时可自动执行（`MIGRATE_ON_START=true`，迁移文件通过 `backend/db/embed.go` 内嵌进二进制）；也可用 `scripts/migrate.ps1` 或 goose CLI 手动执行 |
| 主键 | 业务表使用 `UUID DEFAULT gen_random_uuid()`；高写入日志/样本表（audit_logs、product_events、baseline_records）使用 `BIGSERIAL` |
| 时间 | 统一 `TIMESTAMPTZ`，默认 `now()`；带更新语义的表由 `set_updated_at()` 触发器维护 `updated_at` |
| 编码 | 枚举使用 `SMALLINT`，编码含义集中定义在 `backend/internal/platform/enums/enums.go`；前后端只交换编码，中文标签由 `GET /api/v1/meta/options` 下发 |
| 敏感数据 | 手机号只存 HMAC 摘要（`phone_hash`）与 AES-256-GCM 密文（`phone_encrypted`），不存明文 |
| 软删除 | 用户注销用 `users.deleted_at` + `users.status=4/5`；照片用 `user_photos.deleted_at`；其余业务记录按外键级联清理 |
| 级联 | 用户删除后其资料、偏好、照片、规则、互动、Match、举报等通过 `ON DELETE CASCADE` 清理；审计/事件/计算记录使用 `ON DELETE SET NULL` 保留历史 |

## 2. 迁移清单

| 文件 | 内容 |
|---|---|
| `00001_users_auth.sql` | `set_updated_at()` 触发器函数、users、auth_refresh_tokens、verification_records、consent_records |
| `00002_profiles.sql` | user_profiles、partner_preferences、user_photos |
| `00003_compatibility.sql` | compatibility_questions、user_compatibility_rules，并预置 12 道婚恋价值观问题 |
| `00004_baseline.sql` | baseline_datasets、baseline_records、calculator_runs |
| `00005_social.sql` | interactions、matches、match_outcomes、user_blocks、user_reports |
| `00006_ops.sql` | system_settings（预置 22 个参数）、audit_logs、product_events、regions（预置 34 个省级 + 134 个城市，共 168 行） |
| `00007_indexes.sql` | 面向候选池与漏斗查询的补充索引 |

迁移依赖关系：`00002`~`00006` 中的外键依赖 `users`（`00001`）；`user_compatibility_rules` 依赖 `compatibility_questions`；`baseline_records`、`calculator_runs` 依赖 `baseline_datasets`；`match_outcomes` 依赖 `matches`；`regions.parent_code` 自引用。回滚必须按逆序，goose 的 `down` 一次只回滚一个版本。

### 2.1 迁移执行方式

自动迁移：后端启动时若 `MIGRATE_ON_START=true`（默认），调用 `dbx.Migrate` 以 goose `UpContext` 执行内嵌迁移，幂等。

手动迁移（goose v3.29.0 已安装于 `%USERPROFILE%\go\bin\goose.exe`）：

```powershell
# 仓库内封装脚本（默认连接本地 embedded PostgreSQL：localhost:55432）
pwsh ./scripts/migrate.ps1 up        # 应用全部未执行迁移
pwsh ./scripts/migrate.ps1 status    # 查看每个迁移的执行状态
pwsh ./scripts/migrate.ps1 version   # 当前版本号
pwsh ./scripts/migrate.ps1 down      # 回滚最近一个版本
pwsh ./scripts/migrate.ps1 reset     # 回滚全部（仅开发环境）

# 等价 goose 原生命令（DATABASE_URL 指向目标库）
goose -dir backend/db/migrations postgres "$env:DATABASE_URL" up
```

迁移状态记录在 goose 自动创建的 `goose_db_version` 表中。生产发布流程建议：先备份 → 手动执行迁移 → 再滚动启动新版本；不要依赖多实例同时自动迁移。

### 3.1 主要关系

```
users 1─1 user_profiles / partner_preferences
users 1─N user_photos / user_compatibility_rules / calculator_runs / product_events
users 1─N auth_refresh_tokens / verification_records / consent_records
users N─N users   via interactions（actor_user_id,target_user_id）
users N─N users   via matches（user_a_id < user_b_id 有序存储，唯一约束保证一对只有一条）
users N─N users   via user_blocks（以 blocker 为主键方向）
matches 1─N match_outcomes
baseline_datasets 1─N baseline_records
compatibility_questions 1─N user_compatibility_rules
regions 1─N regions（parent_code 自引用）
```

## 4. smallint 编码字典

以下编码与 `backend/internal/platform/enums/enums.go` 一一对应。数据库 CHECK 约束只限定编码区间（为后续增加编码留空间），语义以本表为准。

| 字段 | 编码 |

| `status`（1~5） | 1 pending 待激活；2 active 正常；3 suspended 已冻结；4 deleted 已注销；5 deletion_pending 注销保留期 |

## 5. 表结构明细

## 8. K 匿名与数据保留

### 8.1 K 匿名（小样本保护）

- 参数：`system_settings.k_anonymity_threshold`，默认 10。
- 规则：任何对用户可见的真实候选数/候选池统计，若实际值小于阈值，统一展示为 `<10`（`DiscoverySummary.eligible_count_text` 等字段），禁止输出精确人数，防止反向识别；数据库内部仍保留真实值用于后台与算法。
- 适用：`GET /api/v1/discovery/summary`、漏斗、敏感性分析、候选列表数量展示。理论市场为统计估算，展示百分比，不展示精确人数。
- 冷启动：真实候选不足时展示早期测试文案（`early_stage_message`），不显示「0 个人」。
- 实现状态：阈值已入库、接口契约已定义；服务端脱敏逻辑随 discovery 模块实现（当前进度见 `docs/07-阶段验收记录.md`）。

### 8.2 数据保留

| 数据 | 策略 |
|---|---|
| 注销账号 | 立即 `discovery_enabled=false`、`status=5`（deletion_pending）、写 `deletion_requested_at`；保留期 `account_deletion_retention_days`（默认 30）后删除/匿名化手机号密文、Profile、Preference、照片；安全/审计数据保留但不含非必要个人信息 |
| 账号删除 | `deleted_at` 软删除 + 级联清理资料；审计/事件/计算记录用 SET NULL 保留历史 |
| Refresh Token | 过期/吊销记录可定期物理清理（当前未实现，待实现） |
| 计算器运行记录 | `calculator_runs` 保存输入/结果快照用于复现与分析；保留时长未配置（待实现） |
| 产品事件/审计日志 | 长期保留用于指标与合规；生产环境建议按年归档（待实现） |

注销保留期清理任务需由 worker 定时执行。当前仓库尚未实现 `cmd/worker` 与清理任务（待实现）；在此之前，注销操作只完成「立即退出婚恋池 + 进入保留期」，到期清理需人工执行。

## 9. EXPLAIN ANALYZE 验证方法与性能目标

### 9.1 性能目标（规格 §58）

| 场景 | 数据量 | 目标 |
|---|---|---|
| 普通候选查询（双向硬筛 + 游标分页） | 100,000 个真实 Profile | P95 < 500ms |
| 计算器理论市场估算（总权重 + 9 维漏斗 + Leave-One-Out） | 100,000 条基线记录 | P95 < 1s |

### 9.2 验证方法

1. 准备数据：启动 PostgreSQL（`deploy/docker-compose.yml` 或 `scripts/dev-db.ps1`），执行迁移，导入/生成 100,000 条 user_profiles 与 100,000 条 baseline_records（生成脚本为验收专用，见下方示例，不随代码提交）。
2. 统计信息：`ANALYZE users, user_profiles, partner_preferences, baseline_records, interactions, matches;`
3. 单条执行计划：对候选查询与计算器聚合 SQL 逐条执行
   ```sql
   EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)
   SELECT u.id, p.gender, p.birth_date, p.city_code, p.height_cm, p.education_level,
          p.annual_income_band, p.marital_status, p.children_count, p.wants_children
   FROM users u
   JOIN user_profiles p ON p.user_id = u.id
   WHERE u.status = 2
     AND u.discovery_enabled
     AND p.profile_completion >= 80
     AND u.id <> $1
     AND p.gender = ANY($2)                       -- 目标性别
     AND p.birth_date BETWEEN $3 AND $4            -- 年龄换算后的出生日期范围
     AND p.city_code = ANY($5)                     -- 城市
     AND p.marital_status = ANY($6)                -- 婚姻状态
     AND (p.height_cm IS NOT NULL AND p.height_cm BETWEEN $7 AND $8)
     AND p.education_level >= $9
     AND p.annual_income_band BETWEEN 1 AND 7 AND p.annual_income_band >= $10
     AND NOT EXISTS (SELECT 1 FROM user_blocks b
                     WHERE (b.blocker_user_id = $1 AND b.blocked_user_id = u.id)
                        OR (b.blocker_user_id = u.id AND b.blocked_user_id = $1))
     AND NOT EXISTS (SELECT 1 FROM interactions i
                     WHERE i.actor_user_id = $1 AND i.target_user_id = u.id AND i.action = 2)
   ORDER BY p.id
   LIMIT 20;
   ```
   关注：是否走 `users_discovery_active_idx`、`user_profiles_gender_city_idx` 等索引；是否出现大范围 Seq Scan；排序是否产生外部排序。
4. P95 采集：对 N（建议 ≥200）组随机条件重复执行，记录耗时并取 95 分位。可使用 `pg_stat_statements` 或应用层压测脚本（`scripts/` 下的验收脚本，待实现/待验收）。
5. 回归：Schema/索引/查询变更后重跑上述步骤，记录到 `docs/07-阶段验收记录.md`。
