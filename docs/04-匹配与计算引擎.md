# 匹配与计算引擎

本文档描述两个纯函数引擎的规则、输入输出与边界口径。引擎代码不访问数据库，可完整单元测试：

- 理论市场引擎：`backend/internal/calculator/`（`model.go`、`engine.go`、`memory_counter.go`、`sql_counter.go`）
- 双向匹配引擎：`backend/internal/matching/`（`model.go`、`engine.go`）

原则：结果必须**可解释、可复现、可测试**；第一阶段不使用机器学习、Embedding、LLM 或向量检索。

---

## 一、理论市场引擎（Calculator）

### 1.1 定位

理论市场回答：「按你设置的条件，基准人口数据集中大约有多少比例的人符合？」数据来源是后台导入的加权匿名样本（`baseline_records`），不是本站真实用户。

理论市场**禁止**输出双向匹配率（基准数据没有他人择偶偏好），只能输出符合条件的人口占比估算。

### 1.2 输入

`calculator.Filter`（字段为 nil 或空表示该维度不限制）：

| 字段 | 类型 | 语义 |
|---|---|---|
| Genders | []int16 | 目标性别编码集合 |
| MinAge / MaxAge | *int | 年龄闭区间（含边界） |
| Cities | []string | 允许城市编码集合 |
| MaritalStatuses | []int16 | 允许婚姻状态 |
| ChildrenStates | []int16 | 子女状态：0 无子女 / 1 有子女（由 children_count>0 折算） |
| WantsChildren | []int16 | 生育意愿编码集合 |
| MinHeight / MaxHeight | *int | 身高闭区间；记录身高为 NULL 时不满足任何身高条件 |
| MinEducation | *int16 | 最低学历（编码比较 `>=`） |
| MinIncome | *int16 | 最低收入区间（编码比较 `>=`） |

输入合法性校验 `Filter.Validate()`：

- 最小年龄不得小于 18；最大年龄不得大于 100；min_age 不得大于 max_age；
- 最小身高不得小于 100；最大身高不得大于 250；min_height 不得大于 max_height。

校验失败返回参数错误（HTTP 400 / `INVALID_ARGUMENT`）。

### 1.3 加权求和

总人口权重 = `SUM(baseline_records.sample_weight)`，按数据集过滤：

```sql
SELECT COALESCE(SUM(sample_weight), 0)::float8
FROM baseline_records WHERE dataset_id = $1;
```

满足条件的权重 = 相同聚合加全部筛选条件（参数全部用占位符传递，动态拼接只拼列名与操作符，避免 SQL 注入）。结果类型为 `float64`；匹配比例 = 匹配权重 / 总权重，总权重为 0 时比例记为 0。

单条样本的语义在 `calculator.Matches` 中定义，内存计数器（单元测试）与 `SQLCounter`（生产路径）必须保持一致；新增条件时必须同时修改两处并补充测试。

### 1.4 固定顺序漏斗

理论市场漏斗按固定 9 个维度依次收紧（`calculator.TheoreticalDimensions`）：

| 顺序 | key | 中文 |
|---|---|---|
| 1 | gender | 目标性别 |
| 2 | age | 年龄 |
| 3 | city | 城市 |
| 4 | marital_status | 婚姻状态 |
| 5 | children_state | 子女情况 |
| 6 | wants_children | 生育意愿 |
| 7 | height | 身高 |
| 8 | education | 学历 |
| 9 | income | 年收入 |

规则：

- 每一步只应用「截至当前维度（含）」的条件（`Filter.upto(key)`）；未启用的维度 `applied=false`，其计数沿用上一步结果，`drop_ratio=0`。
- 每步输出 `count`、`ratio`（相对总人口）、`drop_ratio`（相对上一步的损失比例）。
- 漏斗最终层 `final_count` 用完整条件重新计数（与最后一步一致）；`final_ratio` 为最终匹配比例。
- 引擎固定输出 9 层（未启用维度也占位），保证前端图形稳定。
- 界面必须标注固定说明：`按当前条件顺序计算，改变条件顺序会改变每一步的损失展示`（`calculator.FunnelNote`）。

### 1.5 Leave-One-Out 条件敏感性

对每个「当前生效」的维度，去掉该维度后重新计数（`Filter.Without(key)`）：

- `base_count` = 当前完整条件匹配权重；
- `without_count` = 去掉该条件后的匹配权重；
- `added_count` = `without_count - base_count`；
- `delta_ratio` = `(without_count - base_count) / base_count`（base_count=0 时：若 without_count>0 记 1，否则记 0）；
- 结果按 `delta_ratio` 降序排序（相同则按 key 字典序稳定排序），取前 3 项作为 `top_factors`（「对你候选池影响最大的三个条件」）。

不变量（单元测试覆盖）：取消任一条件后候选权重**不得减少**；未启用维度不进入敏感性列表；无条件输入时敏感性列表为空。

### 1.6 缺失值口径

| 情况 | 口径 |
|---|---|
| 记录 `height_cm IS NULL` 且条件含身高 | 视为不满足身高条件（不能猜测）；无身高条件时不影响 |
| 记录 `annual_income_band = 8`（不愿透露） | 不视为高收入：只有收入区间 1~7 才参与 `>=` 比较；任一收入条件都会排除「不愿透露」样本 |
| 记录 `city_code = ''` 且条件含城市 | 不匹配任何具体城市 |
| 数组条件为空 | 该维度不限制 |
| 总权重为 0（空数据集） | 各项计数与比例为 0，不报错、不产生除零 |
| 匹配权重为 0 且去掉条件后仍为 0 | delta_ratio = 0 |

「缺失不等于 0」的另一面：缺失值不会被打 0 分，而是被排除在筛选之外（无该维度条件时不参与限制）。

### 1.7 缓存键与缓存策略

理论市场计数可缓存（规格 §59）。当前实现（`calculator.Service.computeEstimate` / `cacheKey`）：

- 缓存键：`calc:{dataset_id}:{sha256(json.Marshal(输入 conditions))}`，HEX 编码；
- 存储：`redisx.Store`（Redis；开发环境可退化为内存实现）；
- TTL：10 分钟；
- 缓存内容：`dataset` 元信息 + 完整 `Estimate`（含漏斗与敏感性）；
- 缓存只影响读，计算记录仍每次写入 `calculator_runs`，保证可追溯。

与规格的差异与注意事项（后续优化）：

- 规格建议缓存键包含 `dataset_version`；当前用数据集 UUID 已能覆盖「切换激活数据集」的场景，但**同一数据集重新导入记录后**缓存最长 10 分钟可能陈旧（导入/回滚/激活操作应主动失效缓存，当前未实现，待优化）。
- 条件 JSON 未做归一化：`nil` 与 `[]` 序列化不同，语义相同条件可能生成不同缓存键，只影响命中率，不影响正确性。
- 真实候选池结果**不允许**长期缓存（规格 §59）；匹配结果依赖双方数据，必须实时计算。

### 1.8 输出与文案

`Estimate`（完整 JSON 字段名见 `backend/openapi/openapi.yaml` 的 `CalculatorResult`）：

- `dataset`：数据集名称/版本/来源/免责声明/`is_demo` 标记；
- `total_population`、`matched_count`、`matched_ratio`；
- `funnel`：9 层步骤；
- `sensitivity`、`top_factors`；
- `funnel_note`、`generated_at`。

固定合规文案：

- 理论市场提示（`calculator.MarketNotice`）：`以下结果为基于基准人口数据集的统计估算，用于判断条件筛选的松紧程度，并非精确人数，也不代表双向匹配概率。`
- 注册引导（`calculator.RegisterCTAText`）：`注册后可以查看本站真实用户中，有多少人与你双向满足硬条件。`

禁止把估算结果表述为精确人数（如「全国有 827,431 人」），也禁止输出「双向匹配率」；演示数据集必须显著标注 DEMO，不得冒充真实统计数据。

### 1.9 一次计算的完整流程

1. 校验开关 `calculator_enabled`；
2. 校验条件 `Filter.Validate()`；
3. 读取当前激活数据集（`baseline_datasets.active`；没有则返回 `DATASET_UNAVAILABLE`）；
4. 计算缓存键 → 命中则直接返回；
5. 未命中：`SQLCounter`（总权重 + 漏斗 9 步 + 最终计数 + 每个生效维度一次 LOO）→ 引擎组装结果；
6. 结果写入缓存（10 分钟）；
7. 将输入快照与结果快照写入 `calculator_runs`（游客用 `anonymous_session_id`，登录用户用 `user_id`）；
8. 返回结果（含 `run_id`、数据集信息、合规文案）。

分享：`POST /calculator/share` 为运行记录生成随机 `share_token`（幂等，已存在则复用）；`GET /calculator/share/{token}` 直接读取结果快照，不重新计算。

## 二、匹配引擎（Matching）

### 2.1 定位

只用于「本站真实婚恋市场」。输入双方画像、择偶条件与价值观规则，输出：

- `Eligible`：双向硬条件是否全部满足；
- `PreferenceScore`：条件契合度（我的条件对候选人的满足程度）；
- `CompatibilityScore`：关系观念兼容度（双方价值观答案的互相接受程度）；
- `OverallScore`：综合匹配度；
- 冲突列表、逐维度得分、匹配解释 `reasons`、数据是否不足标记。

引擎不访问数据库；候选查询、Block 过滤、K 匿名、排序分页在服务层与 SQL 层完成。

### 2.2 输入

`matching.Profile`：用户画像（由 `user_profiles` 推导，年龄由 `birth_date` 计算）。

`matching.Preference`：择偶条件，字段与 `partner_preferences` 对应；每个维度有 `*Hard` 布尔标记。

`matching.ValueRule`：价值观规则（`question_id`、分类、`own_answer`、`accepted_answers`、`importance` 0~5、`is_hard`）。

### 2.3 双向硬筛（Hard Filter）

定义：

```
Eligible(A,B) = A 满足 B 的全部硬条件 AND B 满足 A 的全部硬条件
```

实现为两次 `CheckHard`：`CheckHard(B, APref, "b_to_a")`（B 是否满足 A 的要求）+ `CheckHard(A, BPref, "a_to_b")`（A 是否满足 B 的要求），再合并双方价值观硬规则检查。任何一项不满足，`Eligible=false`。

硬条件检查清单（`matching.CheckHard`）：

| 维度 | 何时检查 | 不满足判定 |
|---|---|---|
| 目标性别 `target_genders` | 列表非空（始终视为硬条件） | 候选性别不在列表 |
| 年龄 age | `age_hard=true` | 年龄 < min_age 或 > max_age（闭区间，边界通过） |
| 身高 height | `height_hard=true` | 身高为 NULL，或不在 [min_height_cm, max_height_cm] |
| 城市 city | `city_hard=true` 且允许列表非空 | 城市不在列表 |
| 学历 education | `education_hard=true` | 学历编码 < min_education_level |
| 收入 income | `income_hard=true` | 收入编码 < min_income_band，或收入为 8（不愿透露）/0（未填写） |
| 婚姻状态 marital_status | `marital_status_hard=true` 且列表非空 | 不在允许列表 |
| 子女情况 children | `children_hard=true` 且列表非空 | `children_count>0 → 1` 折算后不在允许列表 |
| 生育意愿 wants_children | `wants_children_hard=true` 且列表非空 | 不在允许列表 |
| 吸烟 smoking | `smoking_hard=true` 且列表非空 | 不在允许列表 |
| 饮酒 drinking | `drinking_hard=true` 且列表非空 | 不在允许列表 |
| 结婚意愿 marriage_intent | `marriage_intent_hard=true` 且 `min_marriage_intent>0` | `IntentRank(候选) < IntentRank(要求)`（编码 1 尽快结婚最强，5 只恋爱不结婚最弱） |
| 价值观硬规则 | 我的规则 `is_hard=true`、`importance>0`、`accepted_answers` 非空 | 对方答案与接受范围无交集；**对方未填写时不视为冲突** |

硬条件不可补偿：任何一项冲突立即 `Eligible=false`，软分再高也不能翻转结论。冲突对象带 `dimension`、`label`、`detail`、`direction`（`a_to_b` 表示 A 不满足 B 的要求；`b_to_a` 表示 B 不满足 A 的要求）。

### 2.4 条件契合度 PreferenceScore

只统计「软条件」：`hard=true` 的维度不参与软分（硬条件已在 Eligible 中一票否决）。维度顺序固定（`matching.PreferenceDimensions`）：

年龄、身高、城市、学历、收入、婚姻状态、子女情况、生育意愿、吸烟习惯、饮酒习惯、结婚意愿。

对每个维度：

- 若该维度对当前偏好「不适用」（例如城市允许列表为空、最低学历为 0、最低收入为 0、min_marriage_intent 为 0、身高条件为开放边界等），则跳过，不计入分母；
- 适用则单项分 = 满足 1 分 / 不满足 0 分；
- 权重取 `partner_preferences.weights` JSONB 中该 key 的值，缺失或 <=0 时默认 1；
- `PreferenceScore = Σ(权重 × 单项分) / Σ(权重)`；总权重为 0 时返回 1（没有可扣分项）。

注意：缺失/未填写字段不会被当作 0 分，而是按上述「适用性」规则处理；唯一的例外是身高：若设置了身高软条件而候选人未填身高，单项分为 0（条件无法满足，但不能算作未知得分）。

### 2.5 关系观念兼容度 CompatibilityScore

以「我的规则」为遍历主干，只有**双方都填写**的题才计入有效分母：

1. 遍历我的每条价值观规则；跳过 `importance=0` 或 `accepted_answers` 为空的规则；
2. 若对方未填写该题（无答案）→ 跳过，不计入分母（禁止「没填写 = 0 分」）；
3. 单项双向打分：
   - 我接受对方答案：+0.5；
   - 对方未设置接受范围（无规则 / importance=0 / 接受范围为空）→ 视为中性，+0.5；
   - 否则，若对方接受我的答案：+0.5；
4. 权重：默认用我的 `importance`；若对方也有该题规则且 `importance>0`，取双方重要度平均值；
5. 累加后 `CompatibilityScore = Σ(权重 × 单项分) / Σ(权重)`；有效题数 `valid_questions` 为参与计算的题数；
6. 同时按题目 `category`（财务/房屋/家务/育儿/职业/异地/父母/彩礼嫁妆/父母同住/消费/冲突/社交）聚合分类得分，供前端展示「财务观念 90%」等维度；
7. 若无任何有效题（总权重为 0），兼容度返回 0，并标记数据不足。

有效题不足阈值：`valid_questions < MinValidQuestions`（默认 6，可由系统参数 `min_valid_compatibility_questions` 覆盖）时：

- 输出 `compatibility_insufficient=true`；
- 前端展示固定文案 **「关系观念数据不足」**（`matching.InsufficientText`），不得生成虚假的精确分数。

### 2.6 综合匹配度 OverallScore

```
Overall = w_pref × PreferenceScore + w_compat × CompatibilityScore
```

- 默认权重 0.4 / 0.6（`matching.DefaultWeights`，与系统参数 `preference_score_weight` / `compatibility_score_weight` 默认值一致）；
- 构造引擎时对权重做归一化（和为 1）；权重和 <=0 时回退默认值；
- 硬筛未通过时仍会计算软分（用于详情页展示「差在哪」），但 `Eligible=false`，软分不能补偿；
- 分数只表示「根据双方填写条件计算出的匹配程度」，不代表婚姻成功概率。免责声明（`matching.Disclaimer`）：`以上分数仅根据双方填写条件计算，不代表婚姻成功概率。`

命名约定：`条件契合度`（PreferenceScore）、`关系观念兼容度`（CompatibilityScore）、`综合匹配度`（OverallScore）。禁止使用「婚姻成功率 87%」。

### 2.7 解释输出

`Result.Reasons` 由可验证的规则生成（示例）：

- 双方硬条件全部满足；
- 性别符合你的期望 / 年龄符合你的要求 / 年龄符合对方要求；
- 婚育意愿一致（双方生育意愿相同且非「未填写」）；
- 同城（双方城市编码相同且非空）；
- 双方学历条件满足。

另外返回：

- `conflicts`：硬条件冲突明细（含方向），用于「你与该用户的硬条件存在 N 项冲突」；
- `preference_detail`：软条件逐维度得分；
- `category_scores`：价值观分类得分；
- `valid_questions`、`compatibility_insufficient`：数据充分性。

文案原则（规格 §70）：描述条件与数据，不做价值判断；不出现「你不合格」「这个女人要求太高」等表述。

### 2.8 引擎入口

| 函数 | 用途 |
|---|---|
| `Engine.Eligible(a, aPref, aRules, b, bPref, bRules)` | 只判断双向硬筛，返回 `(bool, []Conflict)` |
| `Engine.Evaluate(Input)` | 完整评估：硬筛 + 双向软分 + 解释，返回 `Result` |
| `Engine.Weights()` | 返回归一化权重 |
| `CheckHard(candidate, ownerPref, direction)` | 单方向硬条件检查（导出，供测试/工具使用） |

### 2.9 真实市场（Discovery）的引擎接线

真实候选池（`backend/internal/discovery`）复用上述匹配引擎，规则如下：

1. **SQL 双向硬筛**：`buildWhere(includeReverse=true)` 生成两段条件：
   - 我 → 候选：`user_profiles` 的性别/年龄（由 birth_date 换算）/城市/婚姻/子女/生育/身高/学历/收入/吸烟/饮酒/结婚意愿；
   - 候选 → 我：`partner_preferences` 的 `target_genders` 与各 `*_hard` 条件（`cardinality=0` 视为不限制，`NOT hard` 直接放行）；
   - 双方均排除 Block（`NOT EXISTS user_blocks` 双方向）、自己、账号非正常、`discovery_enabled=false`、资料完成度不足、未满 18 岁；
   - 所有用户输入通过占位符参数传递，不拼接 SQL 字符串。
2. **引擎二次校验**：SQL 只是预筛，服务层对每个候选调用 `matching.Engine.Evaluate`，`Eligible=false` 的候选再次剔除，保证 SQL 与 Go 引擎语义一致。
3. **真实池漏斗**（`GetFunnel`）：固定 10 层 = 9 个条件层（目标性别、年龄、城市、婚姻状态、子女情况、生育意愿、身高、学历、年收入）+ 最后一层「同时满足双方硬条件」；每层 `count/ratio/drop_ratio`，`reciprocal_count_text` 做 K 匿名。
4. **真实池敏感性**（`GetSensitivity`）：对 9 个条件逐一 Leave-One-Out 后重算双向候选数，`delta_ratio=(without-base)/base`，按影响降序；不变量：取消条件后候选数不得减少。
5. **概览与冷启动**（`GetSummary`）：`one_way_count`（单向）、`reciprocal_count`（双向）、`eligible_count_text=Anonymize(reciprocal, K)`；`reciprocal < K` 时 `early_stage=true` 并返回早期测试文案，候选列表页不显示「0 个人」。
6. **候选列表与排序**：SQL 拉取最多 `scanLimit=500` 个双向硬筛候选 → 批量加载对方偏好/价值观规则 → 引擎计算三项分数 → 按 `OverallScore` 降序（同分按 UserID）排序 → keyset 游标（`base64(score|userID)`）翻页，禁止 offset 深分页。早期规模下定长扫描保证可用；用户量增长后需把软分/排序下沉 SQL（见待办）。
7. **详情解释**：返回 `reasons`、`dimensions`（价值观分类得分）、三项分数、`compatibility_insufficient`、`my_action`；与对方存在硬条件冲突或已被 Block 时返回 404（不可见）。
8. **互动一致性**：Like/Pass 写入 `interactions`；双向 Like 在事务内创建 `matches`（`user_a_id<user_b_id` + 唯一约束保证幂等，重复 Like 返回同一 match_id）。

### 3.1 Block 规则

Block 不是匹配引擎的一部分（引擎不访问数据库），由服务层与 SQL 保证：

- 一旦 A、B 之间存在任一行 `user_blocks`（任一方向），双向均不可互相发现、不可查看资料、不可 Like/Pass、不可创建 Match；
- 候选查询必须排除两个方向的 Block；
- 已存在的 Match 在 Block 后不可继续操作（Match 状态置 3 已屏蔽）；
- 数据层已具备 `user_blocks` 主键与 `user_blocks_blocked_idx`；discovery 的候选 SQL、详情接口已排除双方向 Block（详情返回 404），interaction 提供 Block/Unblock 接口。
- 已知差距：Block 时**不会**把已存在的 Match 状态改为「已屏蔽（3）」，Match 列表/详情也未按 Block 过滤；规格要求「Block 后已存在 Match 不可继续操作」，当前仅保证不可再发现/查看资料，Match 状态同步待实现（见 07 §4）。
- 实测（2026-11-01）：Block 后目标候选详情 404、候选列表剔除；解除后恢复。
