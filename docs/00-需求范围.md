# 需求范围（Phase 1 ~ 4）

本文档对应根目录 `提示词.txt`（v0.1 规格），说明 MVP 的实现范围与边界。

## 1. 产品定位

不是刷脸 Dating App，而是先让用户知道：

1. 自己的择偶条件在**理论人口市场**中筛掉了多少人（统计估算）；
2. 在**本站真实用户池**中，有多少人与自己双向满足硬条件。

## 2. 两个市场严格区分

| 市场 | 数据来源 | 能算出什么 | 不能算什么 |
|---|---|---|---|
| 理论婚恋市场 | 后台导入的基准人口数据集（加权样本） | 符合条件人口占比、顺序漏斗、条件敏感性 | **双向匹配率**（缺少他人偏好数据） |
| 本站真实婚恋市场 | 平台注册 + 主动入池 + 账户正常的用户 | 单向筛选、双向硬筛、软评分、解释 | —— |

页面与 API 必须显式标注来源，禁止混用、禁止把估算说成精确人数。

## 3. 分阶段功能（对应代码提交 Phase 1 ~ 4）

### Phase 1 计算器 + 理论市场
- 基准数据集管理（CSV 上传 → 校验 → 预览 → 导入 → 激活 → 回滚；同一时刻仅一个 active）
- 理论市场估算：按条件顺序漏斗 + Leave-One-Out 条件敏感性
- 结果分享（share token）
- 游客无需注册即可使用；结果页引导注册查看真实候选池

### Phase 2 注册 / 资料 / 偏好 / 价值观
- 手机号 + 短信验证码（开发环境 mock，生产禁止 mock）
- Access Token 15 分钟 / Refresh Token 30 天（库内仅存 hash，支持吊销与轮换）
- Profile / Partner Preferences / 价值观问题与规则
- 加入真实婚恋池的前置校验（18 岁、资料完成度、协议同意、账户正常）
- 照片上传（MIME 校验、大小与尺寸限制、重编码去除 EXIF 与 GPS）
- 管理端：问题配置、用户查询与冻结

### Phase 3 真实候选池 / 漏斗 / 条件敏感性
- 双向硬条件筛选（Eligible 必须双向满足，不允许软条件补偿）
- 软匹配评分：条件契合度、关系观念兼容度、综合匹配度
- 缺失答案不计入分母；有效价值观题不足 6 道不输出精确分
- 真实池漏斗 + 双向候选率 + Leave-One-Out 敏感性
- 小样本 K 匿名（< 10 统一显示 <10）
- 游标分页（禁止 offset 深分页）

### Phase 4 互动 / Match / 反馈 / 安全 / 运营后台
- Like / Pass（可修改）、双向 Like 生成唯一 Match
- 真实结果反馈（已联系 / 已见面 / 建立关系等），双方均报线下见面则标记 confirmed_meeting
- 举报与 Block（双向不可见、不可互动、不可查看资料）
- 产品事件、运营漏斗、North Star 指标、系统参数与 Feature Flag、审计日志
- 用户注销与保留期清理

## 4. 明确不做（Phase 5 以后）

即时聊天 IM、直播、动态、短视频、LLM 推荐、AI 顾问、支付会员、精确 GPS、视频通话、复杂身份/学历/收入认证、机器学习推荐；以及微服务、Kubernetes、Kafka、Elasticsearch、向量数据库。

## 5. 合规与隐私基线

- 手机号禁止明文存储（HMAC 检索 + AES-GCM 加密）
- 不采集身份证号、精确住址、GPS 坐标、银行卡、工资流水
- 日志禁止输出手机号、JWT、验证码、完整个人资料
- 管理端默认不可见完整手机号；敏感操作写入 audit_logs
